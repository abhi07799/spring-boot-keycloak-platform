# PostgreSQL, JPA, and Flyway

## Database boundary

The backend connects to the application PostgreSQL service only. Keycloak continues to own its independent database and schema.

- Local host connection: `jdbc:postgresql://localhost:5433/platform`
- Compose-network connection: `jdbc:postgresql://app-db:5432/platform`
- The application database credentials are distinct from Keycloak database credentials.

## Start the application database

From the repository root, copy `.env.example` to `.env`, replace the placeholders, and start only the application database:

```bash
docker compose up -d app-db
docker compose ps app-db
```

## Configure the Spring Boot process

Spring Boot does not automatically load Compose's `.env` file into a host process. Supply the datasource values as environment variables before starting the backend.

Bash / macOS / Linux:

```bash
export SPRING_DATASOURCE_URL=jdbc:postgresql://localhost:5433/platform
export SPRING_DATASOURCE_USERNAME=platform
export SPRING_DATASOURCE_PASSWORD='your-app-db-password'
mvn spring-boot:run
```

PowerShell:

```powershell
$env:SPRING_DATASOURCE_URL = "jdbc:postgresql://localhost:5433/platform"
$env:SPRING_DATASOURCE_USERNAME = "platform"
$env:SPRING_DATASOURCE_PASSWORD = "your-app-db-password"
mvn spring-boot:run
```

When the backend itself runs as a Compose service, use `jdbc:postgresql://app-db:5432/platform` instead of `localhost`.

## Flyway migration policy

- Migration scripts live in `src/main/resources/db/migration`.
- Use immutable, versioned names such as `V1__create_user_profiles.sql`.
- Flyway owns schema creation and evolution.
- Hibernate uses `ddl-auto: validate`; it must not create or update production tables.
- Do not combine Flyway with ad-hoc `schema.sql` or `data.sql` initialization.
- Do not edit a migration after it has been applied to a shared database. Add a new migration instead.
- `spring.flyway.clean-disabled=true` prevents accidental schema wipes through Flyway clean.

## Initial user profile table

Migration V1 creates `user_profiles` with:
- UUID primary key generated by the application/JPA provider.
- Keycloak subject identifier with a unique index.
- Full name, email, and mobile number.
- UTC-aware creation and update timestamps.
- Case-insensitive unique email index using PostgreSQL `LOWER(email)`.

No password, password hash, or Keycloak internal database field is stored in the application database. The Keycloak subject is the stable link between the identity and the application profile.

## Administrative data and coordination tables

- V2 adds the mirrored `user_profiles.enabled` flag.
- V3 creates the append-only `admin_audit_events` table for provisioning and account-status actions.
- V4 extends audit records with previous/new application roles and adds the `USER_ROLE_CHANGED` event type.
- V5 adds `user_profiles.authorization_updated_at`, used to reject access tokens issued before a role, status, or session-revocation change.
- V6 adds the `USER_SESSIONS_REVOKED` audit event type.

Password reset and email verification state remain owned by Keycloak; the application profile table does not store passwords, reset tokens, or email action tokens.
Role-management, ADMIN provisioning, account-status, and session-revocation operations use a PostgreSQL session-level advisory lock (no additional lock table or migration is required). The session lock is held across the application transaction and any compensating Keycloak call, including after transaction rollback. The lock uses one pooled connection while the transaction manager uses another, so configure the datasource pool for at least two connections (HikariCP defaults to a larger pool).

## Verify the migrations

Start the app with the datasource environment variables set. On successful startup, Flyway applies all pending migrations and Hibernate validates the mapped entities against the resulting schema.

Inspect the database:

```bash
docker compose exec app-db psql -U platform -d platform
```

Then in psql:

```sql
\dt
\d user_profiles
SELECT installed_rank, version, description, success
FROM flyway_schema_history
ORDER BY installed_rank;
```

The repository test suite keeps the ping endpoint test as a web-slice test so it does not require a running database. For full database verification, start PostgreSQL and run the application locally; confirm that Flyway applies V1 and Hibernate starts with schema validation enabled.
